# Инструкция по запуску
1) Сбилдить докер образ:
```bash
docker build -t my_app .
```
2) Заранить контейнер с пробросом порта:
```bash
docker run --rm -p 8000:8000 my_app
```

# Домены и их ответственность

Домены:
- Пользваотель: отвечает за роль пользователя, его аутенцификацию и выдачу прав, хранение и передачу персональной
информации, удалние и добавление новых пользователей
- Каталог товаров: хранение и поддержание каталога в актуальном состоянии, владеет карточкой товара, атрибутами
- Корзина: добавление и удаление товаров из корзины клиента, поддержвание в актуальном состоянии до заказа
- Поиск и фильтрация: создание/актуализация и хранение индекса производного от каталога для поиска по нему
- Персонализация ленты: построение персонализированных рекомендаций на основе данных о действии клиента (view, click, add-to-cart, buy)
- Заказы: оформление заказов, управление их жизненным циклом и аркестарция на всех этапах после нажатия купить из корзины
- Инвенторизация: ведение учета числа товаров
- Оплата: проведение денежных транзакций, ведение учета
- Нотификация: нотификация клиентов в случае изменения статуса заказа по триггерам

#  Распределение доменов по сервисам
Учитывая, что плохо размывать источник правды, но нормально строить данные повех источника, я старался чтобы каждый сервис
владел только своими доменами и имел поянтную зону ответственности. Очень близкие по сущности домены
(Корзина и каталог) объединены в один сервис, посколько у них высокая связанность по апи и они объединены сущностью "карточка товара"
и различаются лишь юзкейсами, Сервис управдения складом позволяет, как раз надстроен над каталогом и позволяет
уменьшить связанноть сервиса заказов и сервиса взаимодействия с товарами, и не размывать их зоны ответсветнности, 
в случае если слить этот севрис с одним из них

| домен                | сервис                            |
|----------------------|-----------------------------------|
| Пользваотель         | Сервис управления пользователями  |
| Каталог товаров      | Система взаимодействия с товарами |
| Корзина              | Система взаимодействия с товарами |
| Поиск и фильтрация   | Севрвис поиска товаров            |
| Персонализация ленты | Рекомендательная система товаров  |
| Заказы               | Сервис заказов                    |
| Инвенторизация       | Сервис управдения складом         |
| Оплата               | Внутренний платежный сервис       |
| Нотификация          | Сервис нотификаций                |

# Альтернативные варианты декомпозиции, трейд-оффы, финальный выбор
- Вариант A: “Модульный монолит + 1 DB”
Всё внутри одного приложения: users/catalog/orders/payments/notifications/recsys как модули.

Плюсы: проще, быстрее сделать, меньше инфраструктуры.

Минусы: слабая изоляция, сложнее масштабировать, сложно развивать командой.

Trade-off: скорость разработки vs масштабируемость/изоляция.

- Вариант B: “Макро-сервисы (3–4 сервиса)”

Core Service: users + catalog + cart

Order Service: orders

Payment Service: payments/ledger

Notification Service: notifications

Плюсы: меньше сервисов, но уже есть границы и независимые релизы.

Минусы: Core разрастается, возможны конфликты по изменениям.

- Вариант С:
На первом этапе каталог и корзина реализованы в одном сервисе для упрощения интеграции и уменьшения количества межсервисных вызовов. В дальнейшем корзина может быть выделена отдельно как самостоятельный домен.
