# Инструкция по запуску
1) Сбилдить докер образ:
```bash
docker build -t app .
```
2) Заранить контейнер с пробросом порта:
```bash
docker run --rm -p 8000:8000 app
```

# Домены и их ответственность

Домены:
- Пользователь: отвечает за роль пользователя, его аутенцификацию и выдачу прав, хранение и передачу персональной
информации, удаление и добавление новых пользователей
- Каталог товаров: хранение и поддержание каталога в актуальном состоянии, владеет карточкой товара, атрибутами
- Корзина: добавление и удаление товаров из корзины клиента, поддержание в актуальном состоянии до заказа
- Продавец: процессинг продаваемых товаров, публикация новых товаров, изменение старых
- Поиск и фильтрация: создание/актуализация и хранение индекса производного от каталога для поиска по нему
- Персонализация ленты: построение персонализированных рекомендаций на основе данных о действии клиента (view, click, add-to-cart, buy)
- Заказы: оформление заказов, управление их жизненным циклом и оркестрация на всех этапах после нажатия купить из корзины
- Инвенторизация: ведение учета числа товаров
- Оплата: проведение денежных транзакций, ведение учета
- Нотификация: нотификация клиентов в случае изменения статуса заказа по триггерам

#  Распределение доменов по сервисам
- Учитывая, что плохо размывать источник правды, но нормально строить данные поверх источника, я старался чтобы каждый сервис
владел только своими доменами и имел понятную зону ответственности. В свою очередь сервис управления складом, как раз
надстроен над каталогом и позволяет уменьшить связанноть сервиса заказов и сервиса взаимодействия с товарами,
и не размывать их зоны ответственности, в случае если слить этот сервис с одним из них

|----------------------|----------------------------------|
| Пользователь         | Сервис управления пользователями |
| Каталог товаров      | Сервис управления каталогом      |

| Продавец             | Сервис товаров продавца          |

| Персонализация ленты | Рекомендательная система товаров |
| Заказы               | Сервис заказов                   |
| Инвенторизация       | Сервис управления складом        |
| Оплата               | Внутренний платежный сервис      |

# Альтернативные варианты декомпозиции, трейд-оффы, финальный выбор

## Вариант А: Модульный монолит
Описание: Все функции внутри одного приложения с модульной структурой

Сервисы: 1 приложение с модулями (users, catalog, cart, orders, payments, notifications, recsys) + БД (PostgreSQL с разными таблицами)

Плюсы:
- Простота разработки и деплоя
- ACID транзакции из коробки
- Нет сетевых задержек
- Минимальные требования к инфраструктуре

Минусы:
- Сложно масштабировать отдельные части
- Единая точка отказа
- Сложно распараллеливать разработку между командами
- Все компоненты используют один стек технологий

 Trade-off: Простота разработки vs гибкость масштабирования и независимость команд

 ## Вариант Б: Макро-сервисы (3-4 крупных сервиса)
 Описание: Укрупненные сервисы по бизнес-доменам

 Сервисы:
- Core Service (Users + Catalog + Cart)
- Order Service (Orders + Inventory)
- Payment Service (Payments + Ledger)
- Auxiliary Service (Notifications + Search + RecSys)

Плюсы:
- Баланс между простотой и гибкостью
- Меньше межсервисных вызовов чем в микросервисах
- Независимые релизы крупынх частей
- Проще мониторинг чем в микросервисах

 Минусы:
- Core Service может стать узким местом, поскольку его ответственность сильно размывается
- Сложно масштабировать только Catalog или только Cart
- RecSys с ML моделями в одном сервисе с Notifications - разные требования к ресурсам

 Trade-off: Умеренная сложность инфраструктуры vs ограниченная гранулярность масштабирования

 ## Вариант В: Микросервисная архитектура (выбранное решение)
 Описание: Каждый домен - отдельный сервис с собственной БД 

 Сервисы:
- Users Service
- Catalog Service (Products)
- Cart Service
- Seller Service
- Orders Service
- Inventory Service
- Payment Service
- Notifications Service
- Search Service
- RecSys Service

Плюсы:
- Каждый сервис масштабируется независимо (критично для RecSys)
- Свобода в выборе стека под задачу: RecSys - Python/TensorFlow, Catalog - Go, Search - Java+Elasticsearch
- Изоляция сбоев
- Параллельная разработка командами
- Отдельные БД под требования (RecSys - Cassandra для Feature Store, Cart - Redis, Catalog - PostgreSQL)

Минусы:
- Высокая сложность инфраструктуры (K8s, service mesh, distributed tracing)
- Распределенные транзакции требуют Saga паттерн
- Больше сетевых вызовов и латентности
- Сложность тестирования и отладки

Trade-off: Максимальная гибкость и масштабируемость vs высокая операционная сложность

## Ключевые архитектурные решения (внутри выбранного варианта)

### 1. Разделение Каталога и Корзины

Изначально обманчиво хотелось соединить сервисы управления каталогом и корзиной в один, тк оба
взаимодействуют с товарами. Но при этом они очень сильно различаются по ответственности и техническим целям.

Аргументы за:
- Высокая связанность по API
  - Общая сущность карточка товара
  - Меньше межсервисных вызовов

 Аргументы против:
- Разные домены с разной природой:
  - Каталог - это READ-операции, относительно статичные данные
  - Корзина - это WRITE-операции, динамично меняющиеся данные
  - Разные паттерны масштабирования:
    - Каталог можно кешировать (CDN, Redis)
    - Корзина требует консистентности
  - Разные владельцы данных:
    - Каталог владеет продавец (seller)
    - Корзина владеет покупатель (customer)
  - Нарушение приципа Single Responsibility из SOLID:
    - Сервис отвечает и за управление товарами продавцов, и за персональные корзины покупателей


 ### 2. Выделение сервиса складского учета (Inventory)

Изначально можно было включить учет остатков товаров в Catalog Service или Orders Service.

Аргументы за выделение:
- Разделение ответственности: Catalog знает что продается, Inventory знает сколько доступно
- Разные паттерны доступа: Catalog - read-операции, Inventory - write-операции с конкурентными обновлениями
- Изоляция для транзакций: Orders Saga нужен только Inventory API, не весь Catalog
- Специализированные решения: Inventory может использовать Redis с WATCH для оптимистических блокировок
- Применение CQRS: Catalog = Query (read), Inventory = Command (write/reserve/commit)

Аргументы против:
- Дополнительный сервис в инфраструктуре
- Межсервисный вызов при отображении товаров в наличии

Trade-off: Чистота доменной модели и производительность при конкурентных заказах vs упрощение архитектуры

### 3. Паттерн Saga для распределенных транзакций
Покупка товара - это сложная многоступенчатая процедура, которая должна проходить в одной распределенной транзакции.
Для этого используется паттерн проектирования САГА, координирующий выполение распределенной транзакции между сервисами.

Аргументы за:
- Высокая надежность
- Простота масштабирования
- Простота поддержки
- Оркестрация проще в реализации, чем хореграфия, с сервисов, участвующих в транзакции, снимается необходимость
писать компенсации

 Альтернатива - хореография (каждый сервис слушает события и делает свою часть).

 Аргументы за оркестрацию:
- Централизованная логика бизнес-процесса заказа
- Проще отладка и мониторинг (видна вся цепочка в одном месте)
- Явное управление компенсирующими транзакциями
- Меньше coupling между сервисами (только оркестратор знает всю цепочку)

 Аргументы против оркестрации:
- Orders Service становится единой точкой отказа для транзакций
- Дополнительная сложность реализации оркестратора

 Trade-off: Централизованный контроль vs риск единой точки отказа

 ## Финальный выбор

 Выбран Вариант В: Микросервисная архитектура: Высокая операционная сложность микросервисов 
 компенсируется требованиями к персонализации, масштабируемости и изоляции данных.

 ### Обоснование выбора:

1. Требование персонализации ленты:
- RecSys с ML моделями требует масштабирования независимо от остальной системы
- Нужны GPU для инференса моделей - отдельный deployment
- Feature Store требует специализированной БД (Cassandra для time-series данных)

2. Требование высокой доступности каталога:
- Catalog Service - основной read-трафик (просмотр товаров)
- Нужно горизонтальное масштабирование + CDN для карточек
- Отделение от Cart (write-heavy) позволяет оптимизировать отдельно

3. Требование асинхронных уведомлений:
- Notifications через Kafka - event-driven архитектура
- Микросервисы хорошо сочетаются с брокерами сообщений

4. Безопасность платежей:
- Payment Service должен быть изолирован (в отдельном защищенном кластере)
- Отдельная БД для логов платежей

5. Масштабирование поиска:
- Search Service с Elasticsearch требует отдельных ресурсов
- Индексация каталога через события - слабое связывание

6. Ограничение отсутствие общих баз:
- Явное требование задания - каждый сервис владеет своими данными
- В монолите и макро-сервисах сложнее обеспечить полную изоляцию
